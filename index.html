Chapter 01 · Foundations

Claude Code Basics & Installation

What Claude Code is

Claude Code is a terminal-based agentic coding tool that runs across multiple platforms. Rather than passively answering questions, it actively reads files, executes commands, edits code, and solves problems on its own. You describe a desired outcome; Claude Code explores the codebase, forms a plan, and implements a solution while you observe or redirect it.

Where it runs

  • Terminal CLI (primary interface)
  • Native desktop apps, macOS, Windows, Linux
  • Web interface at claude.ai/code
  • IDE extensions, VS Code, JetBrains
Account requirements

Pro, Max, Team, Enterprise, or Console (API) plans. The free claude.ai tier is not supported. Third-party model hosting is also supported: Amazon Bedrock, Google Vertex AI, and Microsoft Foundry.

System requirements

RequirementSpecification
macOS13.0 or later
Windows10 (build 1809) or later
LinuxUbuntu 20.04+ / Debian 10+
RAM4 GB minimum
NetworkInternet connection required
TerminalBash/Zsh (macOS, Linux); PowerShell or Git Bash (Windows)

Installation methods

Method 1, native installer (recommended), includes automatic background updates.

macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash
Windows PowerShell
irm https://claude.ai/install.ps1 | iex

Method 2, package managers (updates are manual).

Homebrew · macOS
brew install --cask claude-code
WinGet · Windows
winget install Anthropic.ClaudeCode

Method 3, npm (requires Node.js 22+).

npm
npm install -g @anthropic-ai/claude-code
Avoid sudo

sudo npm install -g is not recommended. It introduces unnecessary permission and security risk.

Verify the install:

verify
claude --version   # prints the installed version, e.g. 2.1.211
claude doctor      # runs a diagnostic check without opening a session

Your first session

  1. Navigate to your project directory: cd my-project
  2. Start a session: claude
  3. Authenticate (first run only), a browser login prompt appears (command: /login). If the ANTHROPIC_API_KEY environment variable is already set, only key approval is needed.
  4. The session opens in interactive mode at your project root.
  5. Optionally run claude doctor before starting work as a sanity check.

How to onboard yourself

Rather than following a structured tutorial, the most effective approach is to ask Claude Code exploratory questions the way you'd ask a senior engineer who already knows the codebase.

Knowledge-discovery questions

  • “Explain how logging works in this codebase.”
  • “What's the procedure for adding a new API endpoint?”
  • “Which edge cases does CustomerOnboardingFlow handle?”
  • “Describe this project's folder structure.”

Good first practical tasks

  • “Read the README and summarize this project in three lines.”
  • “Add email validation to the login form, then write and run tests for it.”

This approach shortens onboarding time and reduces how often you need a human teammate just to get oriented.

The four-stage workflow cycle

Claude Code sessions follow a predictable, repeating cycle:

The core habit: managing context

The context window is the single most valuable resource in a Claude Code session, performance degrades as it fills up. Chapter 2 covers the full command set; the three to know from day one:

  • /clear, reset context completely between unrelated tasks (use this habitually)
  • /context, visualize current usage and see optimization suggestions
  • /compact [hint], summarize the conversation to reclaim space, e.g. /compact API changes only

Key takeaways

  • Claude Code is agentic: it explores, plans, implements, and verifies. It is not a single-turn Q&A tool.
  • The native installer is the recommended install method; it updates itself automatically.
  • Onboard by asking Claude questions, the way you'd ask a knowledgeable teammate.
  • Every session runs the same four-stage cycle, and you can interrupt or redirect it at any point.
  • Context is the scarce resource from session one, build the /clear habit early.

Chapter 02 · Foundations

Permissions, Plan Mode & Rollback

Permission modes

Five modes control how often Claude must ask for approval before modifying files or running commands.

ModeBehavior
Default (Manual)Read-only actions run automatically; every other action is reviewed by you directly
AcceptEditsReads, file edits, and basic filesystem commands run automatically
PlanRead-only exploration plus classifier-approved commands only
AutoPerforms all actions; a classifier inspects results after the fact
BypassPermissionsSkips prompts and runs everything, intended for isolated/sandboxed environments only
Default changed · 2026.Aug.14

As of August 14, 2026, new sessions on Pro/Max/Team plans default to Auto mode. If you're working in a sensitive repository, check your starting mode rather than assuming Manual.

Switching modes

Cycle through modes with Shift+Tab:

mode cycle
Default → AcceptEdits → Plan → (Auto / BypassPermissions, when conditions allow)

You can also set the mode at launch with flags:

shell
claude --permission-mode plan
claude --permission-mode auto -p "fix lint"

Permission rules · settings.json

Fine-grained control is expressed through three rule lists: deny, ask, allow.

.claude/settings.json
{
  "permissions": {
    "deny":  ["Bash(git push --force *)", "Read(./.env)"],
    "ask":   ["Bash(git push *)"],
    "allow": ["Bash(npm run *)", "Edit(/src/**)"]
  }
}

Evaluation order: deny → ask → allow. The first matching rule wins, regardless of how specific it is.

Common pitfalls

A broad deny rule cannot be punched through with a narrower exception. Bash(ls *) (space + asterisk) requires a word boundary, while Bash(ls*) (no space) matches anything starting with “ls”. A leading / in a path rule is relative to the settings file, not the filesystem root.

Plan Mode: a four-stage workflow

Plan Mode lets you understand a codebase and build a plan without making any changes.

  1. Exploration (Plan Mode), e.g. “Read /src/auth and understand how sessions and login are handled.”
  2. Plan review, e.g. “What files would change if we add Google OAuth? Draft a plan.”
  3. Implementation (mode switch), exit Plan Mode and do the actual coding.
  4. Commit & PR, e.g. “Commit with a descriptive message and open a PR.”
When to skip it

Skip planning for simple typo fixes or other small, clearly-scoped changes, if you can describe the diff in one sentence, just ask directly.

Rollback & recovery

Every prompt in a conversation creates a checkpoint that can be restored.

MethodAction
EscStop execution, context preserved
Esc Esc or /rewindRestore conversation, code, or both to a previous checkpoint
Natural languageAsk Claude directly to undo a change
/clearFully reset context between unrelated tasks
Caution

Checkpoints only track Claude's own edit-tool actions. They do not cover Bash commands or other external processes, and they do not replace git.

Context management commands

CommandFunction
/contextVisualizes current context usage and suggests optimizations
/clearFully resets context, recommended when switching between unrelated tasks
/compact [instruction]Summarizes the conversation to free up space, e.g. /compact focus on API changes
/btwAsk a side question without adding it to conversation history

Key takeaways

  • Five permission modes trade off speed for safety; Shift+Tab cycles between them.
  • Permission rules resolve deny → ask → allow, first match wins, specificity does not override order.
  • Plan Mode separates exploration from execution for anything non-trivial.
  • Esc and /rewind give you reversibility, but they don't replace git for anything outside Claude's own edits.

/advisor, consult a stronger model at decision points

shell

  • The advisor model must be ≥ the main model's tier, a Sonnet 5 session cannot use a Sonnet 4.6 advisor.
  • An Opus 4.7+ main model requires a Fable or Opus 4.7+ advisor; a Fable 5 main model only accepts a Fable 5 advisor.
  • Billed at the advisor model's rates, separate from the main model; consulted only at key decisions, not every turn.
  • Does not invalidate the prompt cache, unlike changing /model or /effort.
  • Anthropic API only, unavailable on Bedrock, GCP, or Foundry.

  • Start at the default (high) for Opus 5 and Sonnet 5.
  • Elevate to xhigh for multi-file refactors, long autonomous tasks, novel architecture decisions, and end-to-end agentic work.

Tokenization & cost notes

  • New tokenizer (Fable 5, Opus 5, Sonnet 5): the same text produces roughly 30% more tokens than the legacy tokenizer used by Opus 4.6 and earlier, and by Haiku 4.5. Comparing only per-token rates across the two families understates real cost.
  • Prompt caching applies automatically; switching models or effort levels invalidates the cache.
  • Adaptive thinking (Opus 5, Fable 5, Sonnet 5): the model self-determines depth; effort governs the extent.
  • Extended thinking (Opus 4.5, Haiku 4.5): a fixed budget via budget_tokens; Haiku 4.5 has no effort control at all.

Fast mode × effort

Fast mode is not a substitute for downgrading the model. It preserves Opus-level intelligence at elevated speed and doubled cost. The two controls are independent:

  • /fast on + /effort xhigh = maximum intelligence and maximum speed, very expensive.
  • /fast off + /effort low = minimum cost and latency, with a quality trade-off.

Key takeaways

  • Four current models, Fable 5, Opus 5, Sonnet 5, Haiku 4.5, trade off intelligence, speed, and cost.
  • /model, /effort, /fast, and /advisor are the four levers; changing model or effort invalidates the prompt cache, /advisor does not.
  • Default to high effort; go to xhigh for genuinely hard agentic work, and down to low/medium for routine tasks.
  • The 2026-generation tokenizer counts ~30% more tokens for the same text, factor that into cost comparisons against Haiku 4.5.

Claude Code is a natural-language tool, but re-explaining a frequent task in a full sentence every time is wasteful. Slash commands (/) are entry points that execute a fixed action consistently.

Command syntax

1. Passing arguments

$ARGUMENTS is the full text typed after the command; $0, $1, etc. are positional arguments.

.claude/commands/fix-issue.md
Fix GitHub issue $ARGUMENTS following our coding standards.

Running /fix-issue 123 substitutes 123 for $ARGUMENTS. Positional args follow shell-style quoting, in /migrate "hello world" Vue, $0 is hello world and $1 is Vue.

2. Shell command injection (dynamic context)

!`command` runs in the shell before Claude sees the content; its output replaces the placeholder.

markdown
## Current changes
!`git diff HEAD`

## Instructions
Summarize the above changes in 3 lines and list the risks.

! is only recognized at the start of a line, or after whitespace. For multi-line shell blocks, use a triple-backtick ```! fenced block.

3. File reference

@path references a file; Claude reads it before responding. You can also point at a directory, e.g. @src/api/handlers/.

markdown
See @src/auth/session.ts for the implementation.

Practical tips

  • Use commands to reduce ambiguity, the more repetitive a task, the more turning it into a command eliminates variance in results.
  • /clear is a performance-management tool. If you've corrected the same issue twice, context is likely contaminated, run /clear and restart with a more specific prompt.
  • Disabling bundled skills: the disableBundledSkills setting turns off all bundled skills except /doctor.
  • Command not showing up? Directories created after the session started may not be detected, restart Claude Code.

Key takeaways

  • Slash commands are an entry point that trades flexibility for consistency.
  • Custom commands are now folded into Skills; existing .claude/commands/ files still work.
  • $ARGUMENTS, !`cmd`, and @file are the three core syntax elements.
  • Actively managing context via /clear, /compact, and /context is what determines session performance.

CLAUDE.md & Project Guidelines

CLAUDE.md is a persistent instruction file, automatically loaded at session start. It eliminates repetitive context-setting by capturing project-specific information Claude should know across every session.

File loading hierarchy

Claude Code searches for CLAUDE.md files across multiple scopes and loads them broader → narrower:

ScopeFile locationPurposePriority
Managed (Enterprise)macOS: /Library/Application Support/ClaudeCode/CLAUDE.md
Linux/WSL: /etc/claude-code/CLAUDE.md
Windows: C:\Program Files\ClaudeCode\CLAUDE.md		Org-wide standards, security policy, compliance1st, not overridable
User~/.claude/CLAUDE.mdPersonal preferences across all projects2nd
Project./CLAUDE.md or ./.claude/CLAUDE.mdTeam-shared, committed to version control3rd
Local./CLAUDE.local.mdIndividual notes, gitignoredLast, highest project-specific priority

Claude also searches upward through the directory tree for additional files, and subdirectory files load on demand as Claude touches files in those folders. Run /context to see exactly which memory files are currently loaded.

Writing principles

The one test that matters

For every line: “would Claude make a mistake without this?” If the answer is no, delete the line.

What to include

  • Bash commands that aren't obvious to Claude
  • Code style rules that differ from language defaults
  • Testing methodology and preferred test runners
  • Branch naming conventions and PR approval workflow
  • Project-specific architectural decisions
  • Development environment quirks, required environment variables, etc.

What to exclude

  • Information readable directly from the code
  • Standard language conventions
  • Detailed API documentation, link to it instead
  • Frequently changing information
  • Per-file descriptions of the codebase
  • Self-evident principles, e.g. “write clean code”
  • Target length: under 200 lines per file, longer files see their rules quietly ignored as context saturates.
  • Be specific: “Use 2-space indentation” beats “format code nicely.”
  • Emphasize what's overlooked: mark frequently-violated rules with IMPORTANT or YOU MUST to raise compliance.
CLAUDE.md
# Code Style
- Use ES modules (import/export); CommonJS (require) is prohibited
- Prefer destructured imports, e.g. import { foo } from 'bar'

# Workflow
- Run type-checking after code changes are complete
- Prefer running a single test over the full suite for performance

File imports · @path

CLAUDE.md can import other files with @path/filename syntax. Imports load at session start. It's an organizational tool, not a context-saving mechanism.

CLAUDE.md
Project overview: @README.md
Available npm commands: @package.json

# Additional Guidelines
- Git workflow: @docs/git-instructions.md
- Personal settings: @~/.claude/my-project-instructions.md
  • Both relative and absolute paths are supported; relative paths resolve from the importing file's location.
  • Recursive imports are allowed, up to a maximum of 4 levels.
  • Paths inside backtick-delimited code are not imported, wrap a path as `@README` to keep it literal.
  • Importing a file outside the working directory (e.g. the home directory) triggers an approval dialog on first run, as a defense against repository-planted exploits.

Path-scoped rules · .claude/rules/

Large projects can modularize guidelines with a .claude/rules/ directory:

tree
your-project/
→ .claude/
    → CLAUDE.md
    → rules/
        → code-style.md
        → testing.md
        → security.md

A paths frontmatter field loads a rule file only when Claude touches matching files, conserving context:

.claude/rules/api.md
---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules
- All endpoints must include input validation
- Use the standardized error response format

Pattern matching: **/*.ts matches TypeScript files anywhere; src/**/* matches anything under src/; src/api/handlers/*.ts targets the handlers directory specifically. Matching uses gitignore-style syntax.

Operational notes

  • Initialize with /init: auto-generates a starter CLAUDE.md by analyzing build commands, test methods, and project conventions. If one already exists, /init proposes improvements rather than overwriting it.
  • Maintain it like code: review periodically, prune obsolete rules, and confirm documented behavior actually happens in practice.
  • Scope precedence: local overrides win functionally for project-specific settings; managed (enterprise) policy can't be circumvented by individual settings.

Key takeaways

  • Four scopes, managed, user, project, local, load broad to narrow, with local taking practical precedence.
  • Include only what Claude can't infer from the code itself; keep it under ~200 lines.
  • @path imports organize content; .claude/rules/ with paths frontmatter loads rules on demand to save context.
  • /init bootstraps a first draft; treat the file as a living document, not a one-time setup step.

Chapter 06 · Extending Claude

Auto Memory

If CLAUDE.md is the instructions you write by hand, auto memory is the notes Claude writes for itself. Even if you write nothing down, Claude stores what it learns while working, build commands, debugging insights, architecture notes, code-style preferences, workflow habits, and carries that knowledge across sessions.

CLAUDE.mdAuto memory
Who writes itYouClaude
What it holdsInstructions / rulesLearning / patterns
ScopeProject · user · organizationPer-repository, shared across worktrees
LoadedFully, every sessionIndex only, first 200 lines / 25KB
Used forCoding standards, workflow, architectureBuild commands, debugging insights, discovered preferences

Use CLAUDE.md to guide behavior; use auto memory when you want Claude to learn on its own from your corrections. Neither is enforced, both are context. For anything that must absolutely be blocked, use a PreToolUse hook instead (Chapter 9).

How it works

Claude doesn't save something every session. It judges for itself whether something will be useful later and records only what's worth keeping. When the interface shows “Saved 2 memories” or “Recalled 2 memories,” Claude is updating or querying its memory directory. Say “always use pnpm, not npm” and it lands in auto memory; say “add this to CLAUDE.md” and it goes there instead.

Storage location & structure

tree
~/.claude/projects/<project>/memory/
→ MEMORY.md          # concise index, loaded every session
→ debugging.md       # detailed debugging patterns
→ api-conventions.md # API design decisions
→ ...                # topic files Claude creates
  • <project> is derived from the git repository, so every worktree and subdirectory of that repo shares one memory directory.
  • MEMORY.md is the index, only the first 200 lines or 25KB (whichever comes first) load at session start.
  • Topic files like debugging.md are not loaded at startup, Claude reads them only when needed.
  • Memory is machine-local; it isn't shared between machines or the cloud.

As MEMORY.md approaches its limit, Claude Code reminds itself to keep one line per entry, move detail into topic files, and merge or delete stale entries. Writes past the limit still succeed, but the overflow is dropped on the next load, prompting a rewrite. YAML frontmatter and HTML comments don't count toward the limit.

Turning it on and off

Auto memory is on by default.

  • Toggle from within a session with /memory (stored as autoMemoryEnabled in ~/.claude/settings.json).
  • Disable it per project: {"autoMemoryEnabled": false} in that project's settings.
  • Disable via environment variable: CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.
  • Relocate storage with autoMemoryDirectory (absolute path, or one starting with ~/).

Memory files are ordinary, editable Markdown, browse them with /memory, and check what's actually loaded with /context.

Subagent memory

Subagents can have their own auto memory too. Turn it on with the memory frontmatter field:

.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews code quality and best practices
memory: project
---

You are a code reviewer. Update your agent memory with patterns, conventions,
and recurring issues you discover during review.
ScopeLocationWhen to use
user~/.claude/agent-memory/<name>/Remember across all projects
project.claude/agent-memory/<name>/Project-specific, shared via version control, recommended default
local.claude/agent-memory-local/<name>/Project-specific, not committed

The main conversation's auto memory is not loaded into subagents, subagent memory lives in its own directory. If auto memory is disabled globally, the memory field is also invalidated.

Usage tips: have it consult memory before starting (“check whether you've seen this pattern before”) and update memory after finishing (“save what you learned”). An explicit instruction to actively manage its own memory compounds institutional knowledge across conversations, not just within one.

CLAUDE.md or auto memory, how to decide

If the knowledge is…Use
A rule I want enforced every timeCLAUDE.md
Something Claude discovers/accumulates on its ownAuto memory
Something that must run at a specific point, without exceptionHooks

Key takeaways

  • Auto memory is the notes Claude writes for itself, learning from corrections and preferences across sessions.
  • Stored at ~/.claude/projects/<project>/memory/; only the index (MEMORY.md, ~200 lines/25KB) loads automatically.
  • On by default; toggled via /memory or autoMemoryEnabled. Fully editable Markdown.
  • Subagents can accumulate their own knowledge via a memory scope, project is the recommended default.

Chapter 07 · Extending Claude

Subagents

A subagent is a separate AI helper dedicated to a specific task, with its own independent context window, its own system prompt, restricted tool access, and separate permissions.

The core value is context protection. Running tests or searching a codebase can produce tens of thousands of tokens of output; piling that into the main conversation degrades performance. Delegate it to a subagent, and that verbose output stays in the subagent's context, only a summary comes back.

  • Context preservation, keep exploration/implementation out of the main conversation
  • Constraint enforcement, restrict which tools can be used
  • Reuse, user-level definitions shared across projects
  • Specialization, domain-specific system prompts

Chapter 08 · Extending Claude

Skills

A Skill is a reusable bundle of knowledge and procedure that extends what Claude can do. Write instructions in a SKILL.md file and Claude adds it to its toolbox, invoking it on its own when relevant, or directly via /skill-name.

When to create one? When you're repeatedly pasting the same instructions or checklist into chat, or when a section of CLAUDE.md has grown from “facts” into “a procedure.”

The decisive advantage: on-demand loading

CLAUDE.md loads in full every session, but a skill's body loads only when actually used. Long reference material costs almost nothing in context until it's needed, put occasionally-needed domain knowledge into a skill, not CLAUDE.md. Skills follow the open Agent Skills standard, so they're portable across multiple AI tools.

Creating your first skill

A skill is a directory + SKILL.md. The directory name becomes the / command.

shell
mkdir -p ~/.claude/skills/summarize-changes
~/.claude/skills/summarize-changes/SKILL.md
---
description: Summarizes uncommitted changes and flags risks. Use when the user
  asks what changed, or wants a commit message / diff review.
---

## Current changes
!`git diff HEAD`

## Instructions
Summarize the above changes in 2-3 bullet points, then list risks such as
missing error handling, hardcoded values, or tests that need updating.
If the diff is empty, say there are no changes.

!`git diff HEAD` is dynamic context injection. It runs before Claude sees the skill, and the real diff is inlined. Asking “what changed?” now triggers it automatically; /summarize-changes invokes it directly.

Hooks

A Hook is a shell command that runs automatically at a specific point in Claude Code's lifecycle. The core idea is determinism: CLAUDE.md instructions are advice you hope gets followed, but hooks execute regardless of Claude's judgment.

Use hooks for things that must happen every single time at a specific point, without exception, formatting after a file edit, blocking dangerous commands, notifying when input is awaited, injecting context at session start. For decisions that need judgment, there are also prompt hooks and agent hooks, which use a model instead of a shell command.

Your first hook, input-wait notification

.claude/settings.json · Linux
{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "notify-send 'Claude Code' 'Claude Code needs your attention'"
          }
        ]
      }
    ]
  }
}

Check registration with /hooks. That menu is read-only; add or edit by directly editing the settings JSON, or ask Claude to write the hook for you.

Without a matcher, a hook fires unconditionally on every instance of its event. Tool events filter by tool name.

.claude/settings.json

        "matcher": "Edit|Write",

      }
    ]
  }
}

"Edit|Write" fires only on file-editing tools (, works as the same separator). MCP tools match as mcp__<server>__<tool>, filterable with a regex like mcp__github__.*.

Input & output, how hooks control Claude

Hooks communicate via stdin (JSON), stdout/stderr, and exit code. Event-specific data arrives on stdin as JSON:

stdin
{
  "session_id": "abc123",
  "cwd": "/Users/sarah/myproject",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",

Exit codeMeaning
0No objection, proceed normally. For UserPromptSubmit/SessionStart, stdout is added to context
2Block the action; stderr is delivered to Claude as feedback so it can adjust
OtherProceed, but show a warning
Not the same as approval

An exit 0 from PreToolUse does not approve the tool, the normal permission flow still applies. To actually block, use exit 2 or the structured JSON output below.

Structured JSON output, with exit 0, printing JSON to stdout gives more precise control:

stdout · PreToolUse
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep (performance)"
  }
}

permissionDecision is allow (skips the prompt), deny (cancels + delivers the reason), or ask (normal prompt). UserPromptSubmit uses additionalContext to inject context on every prompt.

Practical examples

Block edits to protected files · PreToolUse

.claude/hooks/protect-files.sh
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/")

for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
    exit 2
  fi
done
exit 0

Give it execute permission with chmod +x, and register it under PreToolUse/Edit|Write.

Re-inject context after compaction · SessionStart

Compaction summarizes the conversation and can lose important detail. Re-inject the essentials via a SessionStart/compact matcher:

.claude/settings.json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          { "type": "command", "command": "echo 'Reminder: use Bun, not npm. Run bun test before committing. Current sprint: auth refactor.'" }
        ]
      }
    ]
  }
}

Verify work is actually done · prompt/agent hooks

.claude/settings.json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "prompt", "prompt": "Check whether all work is done. If not, respond with {\"ok\": false, \"reason\": \"remaining work\"}." } ] }
    ]
  }
}

If you need to verify actual codebase state, use a "type": "agent" hook that uses tools, e.g. “run the test suite and confirm it passes.”

Hooks and permission modes

PreToolUse hooks fire before any permission mode, even under bypassPermissions or --dangerously-skip-permissions, a deny still blocks the tool. This means a policy enforced this way survives the user switching permission modes. The reverse doesn't hold: a hook's allow can't break through a settings deny rule. Hooks can tighten constraints but never loosen them.

Key takeaways

  • Hook = automation that runs deterministically at a lifecycle point, if CLAUDE.md is advice, hooks are enforcement.
  • Defined in a settings file's hooks block with event, matcher, and command.
  • stdin (JSON), exit code (0/2), and structured JSON output let you block, allow, or inject context into Claude's behavior.
  • Formatting, protected-file blocking, post-compaction re-injection, and pre-completion verification are the signature use cases.

Chapter 10 · Extending Claude

MCP, Plugins & Extensions

Commands, CLAUDE.md, subagents, skills, and hooks all extend Claude Code from the inside. This chapter covers the two ways to extend it outward: MCP (connecting external tools) and plugins (bundling extensions for distribution).

MCP, connecting external tools & data

MCP (Model Context Protocol) is an open standard for AI-tool integration. Connecting an MCP server gives Claude Code direct access to your tools, databases, and APIs.

When to connect one? If you're copy-pasting data from another tool (an issue tracker, a monitoring dashboard) into chat, that's the signal. Connect it, and Claude reads and manipulates that system directly.

  • “Implement the feature described in JIRA issue ENG-4521 and open a PR on GitHub.”
  • “Find the emails of 10 users who used this feature, from PostgreSQL.”
  • “Update the email template with the new Figma design posted in Slack.”

Adding a server · claude mcp add

shell
# 1) Remote HTTP server (most common, supports OAuth)
claude mcp add --transport http notion https://mcp.notion.com/mcp

# 2) Remote SSE server
claude mcp add --transport sse asana https://mcp.asana.com/sse

# 3) Local stdio server (runs as a process on my machine)
claude mcp add --env AIRTABLE_API_KEY=YOUR_KEY airtable -- npx -y airtable-mcp-server

For stdio servers, write the command to run after a double dash --, everything after it is passed straight through to the server.

Scope, where the config is stored

project.mcp.json (committed)Whole team

A project-scoped server (.mcp.json) is pending approval until the repository is trusted, run claude to review and approve it.

Managing · /mcp

Use /mcp within a session to see connection status and handle OAuth. A disconnected HTTP/SSE server auto-reconnects with exponential backoff, up to 5 attempts.

Security

MCP servers are external code. Connect only trusted servers, and activate a project's .mcp.json only after trusting the repository. Anthropic's connector directory lists verified options.

Don't forget CLI tools

MCP isn't the only outward connection. CLI tools like gh (GitHub), aws, and gcloud are the most context-efficient way to reach external services, install gh, and Claude handles issues/PRs/comments on its own. Claude can also learn an unfamiliar CLI: “learn foo with foo --help, then do A.”

Plugins, bundling extensions for distribution

A plugin bundles skills, hooks, subagents, and MCP servers into a single install unit. Community and Anthropic-built plugins install with zero configuration.

shell

  • Using a typed language? A code-intelligence plugin gives accurate symbol navigation and automatic error detection after edits.
  • Because a plugin bundles skills, hooks, agents, and MCP at once, it's ideal for distributing a team's standard workflow.
  • Add a marketplace: /plugin marketplace add <owner/repo>.

Skills/agents provided by a plugin use a plugin-name:skill-name namespace so they don't collide with others.

Chapter 11 · Extending Claude

Orchestration & Workflows

Commands, CLAUDE.md, auto memory, subagents, skills, and MCP/plugins are more powerful woven together than used individually. Claude Code isn't a chatbot that answers once and waits. It's an agentic coding environment: you describe what you want, and Claude explores, plans, and implements.

The constraint everything converges on

The context window fills quickly, and performance degrades as it fills. Context is the single most important resource to manage, keep tracking usage with /context.

Workflow 1, Explore → Plan → Implement → Commit

Jumping straight into coding produces code that solves the wrong problem. Use Plan Mode to separate exploration from execution.

flowchart LR
  A["1. Explore
(Plan Mode)"] --> B[2. Plan]
  B --> C[3. Implement]
  C --> D["4. Commit / PR"]
  C -->|validation failed| B

Fig. 6 · explore, plan, implement, commit

  • Explore, enter Plan Mode, read files and ask questions without making changes. “Read /src/auth and understand how sessions and login are handled.”
  • Plan, “I want to add Google OAuth. Which files change, and what's the session flow? Draw up a plan.” (Ctrl+G opens the plan for direct editing in your editor.)
  • Implement, exit Plan Mode and code to the plan, with validation. “Implement OAuth per the plan, and write and run tests for the callback handler, fixing as needed.”
  • Commit, “Commit with a descriptive message and open a PR.”

Plan Mode isn't a cure-all, for a typo fix or a one-line log addition, just say so directly. Planning earns its keep when the approach is uncertain, multiple files are touched, or the code is unfamiliar.

Workflow 2, always give it a way to validate

Claude stops when a task looks done. Without a validation mechanism, “looks done” becomes the only signal, and you become the validation loop. Give Claude something it can check itself, and the loop closes on its own: work, validate, repeat until it passes.

Validation can be anything readable from the conversation: a test suite, a build's exit code, a linter, a script comparing output to a fixture, or a screenshot compared against a design.

Whole session/goal condition, re-checked by a separate evaluator after every turn
Deterministic gateA Stop hook validates via script; blocks turn completion until it passes

Ask for evidence, not claims, test output, the commands run and their results, screenshots. Reviewing evidence is faster than re-verifying it yourself.

Workflow 3, give precise instructions

Claude can infer intent, but it can't read your mind. The more precise the instruction, the less correction is needed.

StrategyVaguePrecise
Scope the task“Add tests to foo.py”“Write tests in foo.py covering the logged-out edge case. No mocks.”
Point to the source“Why is this API weird?”“Trace ExecutionFactory's git history and summarize how the API came to be this way.”

  • Provide rich context: @file references, pasted images, document URLs (allow domains via /permissions), or piping input in with cat error.log | claude.
  • Have Claude interview you for big features: “I want to build this. Interview me on the technical implementation, UX, and edge cases using the AskUserQuestion tool, and once everything's covered, write the spec to SPEC.md.” Execute the spec in a new session with clean context.

Workflow 4, actively manage your session

The conversation is persistent and reversible, use that.

  • Correct early and often: Esc interrupts while preserving context, Esc Esc//rewind restores a checkpoint, “undo that” works in plain language, and /clear resets between tasks.
  • /clear after two corrections: if you've fixed the same issue more than twice, context is polluted with failed attempts, clear and restart with a better-informed prompt.
  • Manage context aggressively: /clear between unrelated tasks, /compact <instructions> for directed compaction, /btw for side questions that shouldn't enter history.
  • Research via subagents: “Use a subagent to investigate X” keeps exploration in a separate context and returns only a summary.

Workflow 5, scale with automation & parallelism

  • Non-interactive mode: claude -p "prompt" in CI, pre-commit, or scripts. Use --output-format json to parse results; restrict unattended execution with --allowedTools.
  • Parallel sessions: conflict-free isolated checkouts via git worktrees, visual multi-session management in the desktop app, automatic coordination via agent teams.
  • Inter-session messaging (v2.1.224+, macOS · Linux): sessions can message each other, find them with ListAgents, send with SendMessage. A fact learned in one session doesn't need to be re-explained by you to another. Only text Claude wrote is exchanged, not history or files, and in Auto mode, outgoing messages are checked by the classifier too.
  • Writer/reviewer pattern: a fresh context improves review quality, since Claude isn't biased toward code it wrote itself, one session implements, another reviews.
  • File fan-out: for large migrations, build a file list and loop claude -p calls over it.
shell
for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

Auto mode: claude --permission-mode auto -p "fix all lint errors" runs unattended, with a classifier model blocking only dangerous commands.

Chapter 12 · Engineering Practice

Context Engineering

Throughout this course we've repeated one line: “the context window is the most important resource.” Context engineering is the concept that emerged after 2025 as the successor to prompt engineering; Anthropic defines it as “the strategy of curating and maintaining the optimal set of tokens at inference time.”

From prompt engineering to context engineering

  • Prompt engineering, optimizing the text of a single exchange.
  • Context engineering, curating everything the model receives across multiple turns: not just the system prompt, but tool outputs, file contents, memory, and history.

Agents operate iteratively and continuously generate data, so this becomes a cyclically-refined task, every inference asks “what configuration of information will best elicit the desired behavior?”

Context is a finite resource, context rot

Key insight

LLMs have an “attention budget,” much like human working memory. As tokens increase, that budget depletes, and the ability to accurately recall and focus on information degrades. This is called context rot.

  • Transformers create n² pairwise relationships between tokens, so as scale grows, attention spreads more thinly.
  • The degradation isn't a cliff but a gradual gradient. It doesn't suddenly stop working, it blurs gradually.
  • Filling a 1M-token window to the brim does not make things better. The goal is the smallest set of high-signal tokens that maximizes the probability of the desired outcome.

The four areas of curation

1. System prompt, the right altitude

Too low (brittle)Too high (vague)
Hardcoding complex if/else logic → brittle, maintenance hellVague high-level guidance → fails to drive behavior

The sweet spot: guidance specific enough to steer behavior, yet flexible enough to give strong heuristics. Divide sections with XML tags or markdown headers, start from a minimal prompt, and add clarity/examples per failure case. “Minimal” doesn't mean “short”. It means the minimum information that fully paints the expected behavior (the same spirit as Chapter 5's “would removing this cause a mistake?” test).

2. Tool design, minimal, clear, self-contained

Each tool should be self-contained, robust to errors, and have an extremely clear purpose. A bloated toolset creates overlapping functionality that blurs judgment, if a human engineer can't tell which tool to use, neither can the model. Return only the information needed, to maximize token efficiency.

3. Examples (few-shot), diverse, canonical examples

For an LLM, an example is worth a thousand words. But listing edge cases like a laundry list is an anti-pattern that only bloats context, curate a small number of diverse, canonical examples representing the full range of expected behavior (quality over quantity).

4. Retrieval strategy, just-in-time vs. pre-retrieval

  • Pre-retrieval: load everything upfront, fast, but risks staleness.
  • Just-in-time: carry only lightweight identifiers, file paths, URLs, queries, and load via tools only when needed. This is how Claude Code handles large data without reading it wholesale, using targeted head/tail/grep-style queries.
  • Hybrid (recommended): preload some things (e.g. CLAUDE.md) for speed, and explore the rest autonomously via glob/grep.
  • Progressive disclosure: discover needed context progressively while exploring, keeping only what's needed in working memory, the same principle as human cognition.

Three techniques for long-running tasks

TechniqueWhat it isThis course's implementationSuited to
CompactionSummarize history and restart with a compacted version + recent context/compact, auto-compactionLong back-and-forth exchanges where conversational flow matters
Structured notes / agent memoryWrite notes externally and recall them when neededAuto memory · MEMORY.mdIterative development with todo milestones
Subagent architectureSpecialized subagents handle work with a clean context, returning only summariesSubagentsComplex research where parallel exploration helps

A subagent may explore tens of thousands of tokens but return only a 1,000–2,000 token summary to the main thread. The art of compaction is to first maximize recall (capture everything), then increase precision (remove what's unnecessary), the easiest win is deleting old tool-call results, since raw output deep in history is rarely reused.

Practice in Claude Code

  • Continuously observe what's eating the attention budget with /context.
  • Reset with /clear at every task switch; direct compaction with /compact <instruction>.
  • Keep CLAUDE.md short and at the right altitude; put occasionally-needed material into on-demand skills.
  • Isolate high-output exploration into subagents to protect the main context.
  • Keep tools/MCP minimal and clear, overlapping tools blur judgment.
Philosophy

The better the model gets, the less fine-grained instruction it needs, and the more autonomy can be handed to the agent. Still, the principle holds: do the simplest thing that works.

Key takeaways

  • Context engineering curates everything the model sees across turns, not just a single prompt.
  • Context rot is gradual, not a cliff. The goal is the smallest high-signal token set, not maximum fill.
  • Curate the system prompt, tool design, few-shot examples, and retrieval strategy deliberately.
  • Compaction, structured notes, and subagents are the three practical techniques for tasks that outlast one context window.

As of 2026, the discipline of working with AI agents is organized into four layers. This chapter covers the top two, harness engineering and loop engineering, plus the community's most popular techniques.

Harness engineering

Core formula

Agent = model + harness. A raw model only generates text; wrapped in a harness it becomes an autonomous agent that maintains state, executes tools, learns from failure, and enforces constraints.

A striking data point: with the same underlying model, Terminal-Bench scores reportedly jumped dramatically inside Claude Code's sophisticated harness compared to a simple setup, from around rank 30 to around rank 5. No model change, just a better harness.

Two directions, guide vs. sensor

  • Guide (feedforward): provide context/rules before generation, CLAUDE.md, specs, bootstrap templates.
  • Sensor (feedback): inspect results after generation and trigger self-correction, linting, layer-separation tests, requirement-verification review agents.

The “skill issue” reframe

Treat agent failures not as model limitations but as a configuration problem. When a mistake occurs, don't file it away as an anecdote, engineer around it: add a lint hook, fix the rules doc, insert a verification step. Failure becomes a permanent signal rather than a one-off story, and the harness improves like a ratchet. The harness doesn't disappear as models improve. It moves: old mitigations become unnecessary, but new failure modes appear that demand new constraints.

Loop engineering

A line that captures the shift

“I no longer prompt Claude. I write loops that prompt Claude.”, Boris Cherny, who leads Claude Code, 2026. Control shifts from the person to the system.

Loop engineering combines persistent instructions, skills, subagents, and hooks so an agent repeats on its own: gather context → act → verify → self-correct → until a measurable goal is reached.

/goal, the cleanest entry point

Enter a completion condition once, and after every turn a Haiku-tier evaluator reads the transcript and judges whether it's been met, repeating until it is.

Ralph loop, build, test, verify

The representative pattern for autonomous code-generation loops.

Fig. 9 · the Ralph loop: a hook intercepts an early exit and reinjects the goal into a new context; each iteration reads prior state from the filesystem and gets test results back

  • A hook intercepts the model's attempt to end the session and reinjects the original prompt into a new context to keep it working.
  • Each iteration starts clean, but reads prior state from the filesystem (structured notes).
  • After every step, a hook runs the test suite and feeds back failures along with error text.

Planner/evaluator separation

Separate the agent that generates from the agent that grades, since models tend to grade their own work optimistically. This is the principle behind adversarial review, where a verification subagent in a new context looks only at the diff and pushes back.

The risk of loops

An unattended loop is also an unattended-mistake loop. A loop must always include sensors, gated by the auto-mode classifier (Chapter 2), a /goal evaluator, or a Stop hook.

Latest Model Prompt Guide

The Chapter 3 lineup, Opus 5, Fable 5, Sonnet 5, is far smarter and more autonomous than previous generations. Existing Opus 4.8 prompts still work well, but because these models behave more autonomously, some habits need to be tuned in the opposite direction. This chapter, based on Anthropic's Opus 5 prompting guide, collects the patterns adjusted most often in practice.

Big principle

The better the model, the less you should instruct it. Scaffolding added to push older models, forced verification, re-confirmation instructions, triggers overcorrection in newer models and wastes tokens. Removing such instructions is itself an improvement.

1. Responses got longer, instruct for conciseness

Opus 5's default user-facing responses run longer than previous Opus. effort only controls how much it thinks, not how much it says, lowering effort doesn't reliably shorten visible responses. Length must be explicitly prompted.

system prompt
Keep responses focused, brief, and concise. Keep disclaimers and caveats short,
and spend most of the response on the main answer. When asked to explain something,
give a high-level summary unless an in-depth explanation is specifically requested.

In long system prompts, a short reminder near the end works well too:

system prompt · excerpt
<tone_preference>
Keep outputs reasonably concise.
</tone_preference>

2. It narrates progress a lot, specify a cadence

During agentic work, Opus 5 frequently previews “what I'm about to do now,” and per-turn output runs longer than before. Specifying the communication style controls this.

system prompt
Before your first tool call, say in one sentence what you're about to do.
While working, give a brief update only when you find something important or
change direction. When you finish, lead with the outcome: your first sentence
should answer "what happened" or "what did you find," with supporting detail after.

Positive examples of “do it this way” work better than negative “don't do this” instructions, the same lever works if you want more narration, or a different style.

3. File outputs also got longer, calibrate length

Separately from conversational verbosity, files Opus 5 writes to disk, reports, markdown, summaries, are also longer than before. If your product has Claude write documents, specify a length criterion.

system prompt
Match the length of written documents to what the task needs: cover the substance,
but do not pad with filler sections, redundant summaries, or boilerplate.

4. It self-verifies, remove verification instructions, constrain scope

Opus 5 verifies its own work even without being told to. Remove prompt instructions like “add a final verification step for non-trivial tasks”, in newer models these trigger over-verification and waste tokens (legacy harness scaffolding has the same issue).

Opus 5 also tends to add unrequested steps or widen scope. For narrow tasks, constrain it explicitly:

system prompt
Deliver what was asked, at the scope intended. Make routine judgment calls yourself,
and check in only when different readings of the request would lead to materially
different work. If the request seems mistaken or a better approach exists, say so in
a sentence and continue with the task as asked rather than quietly narrowing,
widening, or transforming it. Finish the whole task, and stop short of actions that
are clearly beyond what was asked.

5. It delegates to subagents more actively, put a cap on it

Delegation pays off for genuinely independent, large tasks, but applied to small tasks it doubles cost and time.

system prompt
Delegate to a subagent only for large tasks that are genuinely independent and
parallelizable, such as a wide multi-file investigation. Do not delegate work you can
finish yourself in a handful of tool calls, and do not use subagents to verify or
double-check your own work. If one subagent can complete the task, use one rather
than several, and keep spawn counts low.

6. It self-corrects, remove re-confirmation instructions

Opus 5 catches and fixes its own mistakes on its own. Instructions like “double-check your answer” overlap with existing behavior and only add cost. Narration correcting earlier statements has increased, though, which can be distracting, keep only meaningful corrections:

system prompt
Only correct an earlier statement when the error would change the user's code,
conclusions, or decisions. State corrections plainly and briefly, then continue.
For slips that change nothing for the user, make the fix and move on without noting it.

7. Artifacts when thinking is turned off

Opus 5 has thinking on by default, and disabling it is only possible at effort high or below. Turning it off occasionally produces two artifacts: a tool call leaking into visible text instead of executing, or internal tags like <thinking> leaking into the response.

Best mitigation

Don't turn off thinking. Lower effort instead to control cost. In most tasks, “thinking on + low effort” beats “thinking off.” If you must turn it off, address both artifacts with one instruction (avoid naming the tag specifically, since that increases leakage):

system prompt
When you use a tool, you may say a brief sentence first. If no tool can express what
the user asked for, say so instead of guessing. Do not include internal or system
XML tags in your response.

Migration notes · Opus 4.8 → Opus 5

  • Opus 5 works well out of the box with existing 4.8 prompts, the patterns above are adjustments “for when tuning is needed.”
  • Thinking is on by default now; disabling it is only possible at effort high or below.
  • It's strongest when given a complete task specification up front and left to autonomous execution, the same “be specific” principle from Chapter 11.
  • If you carried over effort defaults from an older model, re-sweep them against your own eval set.

Key takeaways

  • Newer models need less scaffolding, not more, remove verification/re-confirmation instructions written for older models.
  • Responses, narration, and written files are all longer by default, prompt explicitly for the length you want.
  • Cap subagent delegation for small tasks; it pays off only for genuinely large, independent work.
  • Prefer “thinking on + low effort” over disabling thinking, which can leak tool calls or internal tags into visible text.

Cost & performance management

  • Check API usage/cost with /usage. For lower cost, lower the model or effort.
  • Prompt caching: large, repeated context (e.g. CLAUDE.md) is cached automatically for up to 90% savings; switching models mid-session invalidates the cache, so avoid frequent switching.
  • Release channels: native installs auto-update. In /config's auto-update channel, choose latest or stable (about a 1-week delay, avoiding regressions).
  • Sessions continue after hitting a usage limit (v2.1.234+): once the claude.ai usage limit resets, Claude Code automatically resumes. Turn this off in /config's “continue automatically at usage limit” setting if unwanted.
  • Run claude doctor any time to diagnose install/config state.

Using it safely, quick checklist

  • Use Manual (default) or Plan Mode for sensitive work, and Auto mode for trusted work (Chapter 2). New sessions on Pro/Max/Team now start in Auto mode, check your starting mode on sensitive repos.
  • Behavior that absolutely must be blocked belongs in a hook, not CLAUDE.md advice.
  • Unattended execution (loops) must always be gated by verification: tests, /goal, or verification subagents.
  • Review external assets, subagents, skills, plugins, MCP, before adopting them.
  • Undo via /rewind and checkpoints, but remember Bash and external changes aren't captured, git is the final safety net.

Key takeaways

  • Sessions are branchable and resumable, name and fork them rather than letting one conversation absorb every task.
  • Bundled skills like /code-review, /security-review, and the deeper cloud-based ultra variant cover most quality/security needs out of the box.
  • Prompt caching and avoiding mid-session model switches are the biggest cost levers.
  • Hooks enforce what must never be skipped; everything unattended needs a verification gate.
